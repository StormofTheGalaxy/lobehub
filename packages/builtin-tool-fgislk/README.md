# ФГИС ЛК: отчётность (`lobe-fgislk`)

Встроенный инструмент LobeHub для подготовки и проверки XML-отчётности лесной
отрасли. Сейчас поддержан «Отчёт о воспроизводстве лесов и лесоразведении»
(форма 1-ВЛ, приказ Минприроды России от 18.03.2025 № 112).

Результат работы — файл `.xml`, который лесопользователь подписывает своей
электронной подписью и подаёт во ФГИС ЛК.

## Почему это работает без 1С и без портала

Формат отчёта государственный и открытый. Рослесхоз публикует и XSD-схемы,
и все справочники: <https://rosleshoz.gov.ru/information-systems/fgis-lk-information/sampledoc-xsd/>

Справочники распространяются прямо внутри XSD, перечислениями с описанием:

```xml
<xs:enumeration value="100405">
  <xs:annotation><xs:documentation>Лиственница даурская</xs:documentation></xs:annotation>
</xs:enumeration>
```

Поэтому множество допустимых значений известно заранее и проверяется офлайн,
а модель может искать код по наименованию вместо того, чтобы его вспоминать.

В `data/` лежат ровно эти официальные файлы:

| Что | Версия | Источник |
| --- | --- | --- |
| `schemas/forestReproduction_v3.0.7.xsd` | 3.0.7, действует с 05.05.2026 | `ForestReproduction_3.0.7.zip` |
| `schemas/common3.4/` (22 файла) | common 3.4 | `common_3.4.zip` |
| `nsi/measures_1vl.csv` | 88 строк формы | приказ № 112, приложение № 2 |

ФГИС ЛК принимает действующую версию схемы и две предыдущие.

## Как устроена защита от ошибок

Отчётность не терпит «почти правильного» документа, поэтому ошибки блокируются
конструкцией, а не проверяются постфактум.

1. **Модель не пишет XML.** Она заполняет структуру данных, а разметку собирает
   `Builder`, который идёт по типам из XSD. Порядок элементов берётся из
   `xs:sequence`, пропуск обязательного элемента — исключение.
2. **Незнакомое поле — ошибка.** И на прикладном уровне (`report.ts`), и при
   сборке по схеме (`build.ts`). Опечатка `organisation` вместо `organization`
   не превратится в пустой раздел реквизитов.
3. **Коды не подбираются «похоже».** Наименование сопоставляется со справочником
   только точно; похожие значения показываются в тексте ошибки, но выбирает из
   них человек. Причина буквальная: «Дерево обыкновенное» — подстрока названия
   «Земляничное дерево обыкновенное (крупноплодное)».
4. **Код строки отчёта и единицу измерения подставляет карта формы,** а не
   пользователь и не модель. Если наименование подходит нескольким строкам
   («из него — посадка лесных культур, всего» встречается 4 раза), сборка
   останавливается и просит указать код.
5. **Невалидный файл не появляется на диске.** Сборка идёт во временный файл,
   и только успешная валидация `xmllint` переносит его в целевой путь.
6. **Смысловые проверки поверх XSD:** соответствие кода строки и единицы форме,
   число знаков после запятой (сноска <3>), арифметика «всего / в том числе /
   из него», вложенность учётных номеров ГЛР, ссылки фотофиксации на вложения,
   контрольные суммы MD5, JPEG не менее 5 Мпикс и не более 12 точек.
7. **`buildReport` и `migrateReport` требуют подтверждения человека**
   (`humanIntervention: 'always'`) — их нельзя выполнить в автоматическом режиме.
8. **Вердикт один и однозначный.** Поле `ready` истинно, только если документ
   валиден и не содержит находок уровня ОШИБКА.

Чего инструмент не проверяет и проверить не может: соответствие учётных номеров
выписке из ГЛР, наличие документа-основания во ФГИС ЛК, соответствие объёмов
фактически выполненным работам. Это выводится пользователю чек-листом при каждой
успешной сборке.

## Требования к окружению

- **xmllint** (libxml2) на сервере, где выполняется инструмент.
  В образ, который собирает CI, он уже входит: `libxml2-utils` ставится в базовом
  слое, а бинарник с фактическими зависимостями (их список берётся через `ldd`)
  копируется в distroless-слой. Стадия `app` проверяет, что `xmllint` и `node`
  действительно запускаются и схемы на месте, — иначе сборка падает и образ не
  публикуется. Прирост образа: около 43 МБ в распакованном виде на архитектуру,
  из них ~36 МБ — libicu72, от которой на Debian bookworm зависит libxml2.
  Для локальной разработки: Linux — `apt-get install libxml2-utils`,
  в macOS входит в состав системы.
  Без xmllint внешняя проверка по XSD не выполняется, файл не записывается, а в
  ответе прямо сказано, что документ нельзя считать проверенным.
  Убрать эту зависимость и её вес можно, перейдя на libxml2, собранную в
  WebAssembly, — тогда инструмент заработает и на Vercel.
- Каталог данных ищется в таком порядке: переменная окружения
  `FGISLK_DATA_DIR`, затем `data/` рядом с пакетом, затем
  `packages/builtin-tool-fgislk/data` относительно рабочего каталога.
  Переменная нужна, когда Рослесхоз выпустит новую версию схемы: достаточно
  положить новый комплект и указать путь, пересборка приложения не требуется.

## Обновление схем

1. Скачать новые архивы со страницы XSD-схем Рослесхоза.
2. Положить `forestReproduction_vX.Y.Z.xsd` и каталог `commonN.M/` в `data/schemas/`.
3. Поправить `mainXsd()` и `COMMON_VERSION` в `src/engine/paths.ts`.
4. Прогнать тесты: структура генератора берётся из схемы, поэтому чаще всего
   ничего больше менять не нужно.

## Тесты

```bash
pnpm vitest run packages/builtin-tool-fgislk
```

Тесты используют вымышленные данные: реальные отчёты содержат персональные
данные и в репозиторий не кладутся.

Отдельно, вручную, выполнена сверка с реальным отчётом, уже прошедшим приёмку
во ФГИС ЛК: движок собрал документ из исходных данных, и все 146 значений
совпали с принятым файлом. Расхождения только в служебных идентификаторах,
которые у каждой выгрузки свои. Сам эталон в репозиторий не кладётся —
он содержит персональные данные подписанта и реквизиты договора.
